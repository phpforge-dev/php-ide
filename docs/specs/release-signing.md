# Release signing — what the release owner has to create

Status: the workflows are ready and skip every signing step whose secrets are missing. Nothing in this
list has been created: keys, certificates, repository secrets and variables belong to the release owner
and must never be generated by an agent or committed.

Where each value goes: **GitHub → repository `phpforge-dev/php-ide` → Settings → Secrets and variables →
Actions**. *Secret* = "Secrets" tab; *variable* = "Variables" tab. Names are case-sensitive.

Each group below is all-or-nothing. `scripts/release-signing.mjs` stops the workflow before building
when a group is only partly configured (it names the missing entries, never the values), so a typo
cannot silently produce an unsigned or half-signed release.

| Without the group | With the group |
| --- | --- |
| No `latest.json`; the IDE offers only the manual download page | Updater signatures + `latest.json`; installed IDEs update themselves |
| macOS DMG with the ad hoc signature (Gatekeeper warning, as today) | Developer ID signature, notarized and stapled `.app` and DMG |
| Unsigned NSIS installer (SmartScreen warning, as today) | Authenticode-signed installer (and signed updates on Windows) |

## 1. Tauri updater key (required for automatic updates)

1. On a trusted machine, from the repository root:
   ```bash
   npx tauri signer generate -w ~/.tauri/php-ide-updater.key
   ```
   Choose a strong password when asked. This writes `php-ide-updater.key` (private) and
   `php-ide-updater.key.pub` (public, one base64 line).
2. Back up the private key and its password offline (password manager + offline copy). **If it is lost,
   installed IDEs can never update automatically again**: every user would have to reinstall manually
   from a build that trusts a new key. If it leaks, an attacker can sign updates; rotate it at once with
   a manually installed release.
3. Create:

| Kind | Name | Value |
| --- | --- | --- |
| Variable | `PHP_IDE_UPDATER_PUBLIC_KEY` | Contents of `php-ide-updater.key.pub` |
| Secret | `TAURI_SIGNING_PRIVATE_KEY` | Contents of `php-ide-updater.key` |
| Secret | `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | Its password (omit only for a key without password) |

The public key is compiled into the IDE. Releases built before it existed (0.2.19 and older) do not
trust any key, so their users install the first signed release manually once; from then on updates
arrive automatically. A locally built DMG must also be built with `PHP_IDE_UPDATER_PUBLIC_KEY` in the
environment, otherwise that install never offers automatic updates — prefer the workflow DMG.

## 2. Apple Developer ID and notarization (macOS)

Needs a paid Apple Developer Program membership (Account Holder role to create the certificate).

1. **Certificate.** In Xcode → Settings → Accounts → Manage Certificates → "+" → *Developer ID
   Application* (or developer.apple.com → Certificates → "+" → Developer ID Application, using a CSR from
   Keychain Access). In Keychain Access, export the certificate **with its private key** as `.p12` and a
   strong export password.
2. **Identity.** `security find-identity -v -p codesigning` prints it, e.g.
   `Developer ID Application: Your Company (ABCDE12345)`.
3. **Notarization credentials** — choose one:
   - *Recommended*: App Store Connect → Users and Access → Integrations → App Store Connect API →
     Team Keys → "+", access *Developer*. Download `AuthKey_<KEYID>.p8` (only once) and note the
     Key ID and Issuer ID.
   - *Alternative*: an Apple ID with an app-specific password (appleid.apple.com → Sign-In and Security
     → App-Specific Passwords) and the 10-character Team ID.
4. Create:

| Kind | Name | Value |
| --- | --- | --- |
| Secret | `APPLE_CERTIFICATE` | `base64 -i DeveloperID.p12 \| pbcopy` output (single line) |
| Secret | `APPLE_CERTIFICATE_PASSWORD` | The `.p12` export password |
| Secret | `APPLE_SIGNING_IDENTITY` | The full identity string from step 2 |
| Secret | `APPLE_API_KEY` | API Key ID (*recommended option*) |
| Secret | `APPLE_API_ISSUER` | Issuer ID (*recommended option*) |
| Secret | `APPLE_API_PRIVATE_KEY` | Full text of `AuthKey_<KEYID>.p8`, including the BEGIN/END lines |
| Secret | `APPLE_ID` | Apple ID e-mail (*alternative only*) |
| Secret | `APPLE_PASSWORD` | App-specific password (*alternative only*) |
| Secret | `APPLE_TEAM_ID` | Team ID (*alternative only*) |

Configure either the three `APPLE_API_*` secrets or the three Apple ID secrets. A Developer ID
certificate without notarization credentials is rejected on purpose: a signed but un-notarized download
is still blocked by Gatekeeper. With the group configured, the build signs the app with the hardened
runtime, Tauri notarizes and staples the `.app`, the workflow notarizes and staples the DMG, and
`spctl` must accept both before anything is uploaded.

## 3. Windows code signing (NSIS installer)

Choose **one** option; configuring both stops the workflow.

### Option A — Azure Trusted Signing (recommended)

1. Azure portal: create a *Trusted Signing account* (note its region endpoint, e.g.
   `https://eus.codesigning.azure.net`), complete identity validation and create a *Public Trust*
   certificate profile.
2. Microsoft Entra ID → App registrations → new registration; create a client secret.
3. On the Trusted Signing account, grant that app the role **Trusted Signing Certificate Profile Signer**.
4. Create:

| Kind | Name | Value |
| --- | --- | --- |
| Secret | `AZURE_CLIENT_ID` | Application (client) ID |
| Secret | `AZURE_CLIENT_SECRET` | Client secret value |
| Secret | `AZURE_TENANT_ID` | Directory (tenant) ID |
| Variable | `AZURE_TRUSTED_SIGNING_ENDPOINT` | `https://<region>.codesigning.azure.net` |
| Variable | `AZURE_TRUSTED_SIGNING_ACCOUNT` | Trusted Signing account name |
| Variable | `AZURE_TRUSTED_SIGNING_PROFILE` | Certificate profile name |

The Windows job installs `trusted-signing-cli` and Tauri calls it for the app executable and the NSIS
installer.

### Option B — Authenticode certificate file (OV code-signing `.pfx`)

Only for a certificate that can be exported as `.pfx`. Since June 2023 new OV/EV certificates are
issued on hardware tokens/HSMs and cannot be exported; for those use option A (or a CA cloud-signing
service, which would need its own `signCommand`).

| Kind | Name | Value |
| --- | --- | --- |
| Secret | `WINDOWS_CERTIFICATE` | `base64 -i certificate.pfx` output (single line) |
| Secret | `WINDOWS_CERTIFICATE_PASSWORD` | The `.pfx` password |

The job imports it into the runner's user store, signs with SHA-256 and a DigiCert timestamp, and
`Get-AuthenticodeSignature` must report `Valid`.

## 4. Running a release

1. Merge, bump the version and create the release tag as today.
2. **With the updater key configured**: run **Signed IDE updates** (`signed-updates.yml`) with the tag.
   It builds macOS DMG, Windows NSIS and Linux deb/AppImage, signs whatever is configured, publishes the
   installers and checksums, the updater archives and signatures, and `latest.json` last — only after
   every platform succeeded. Do not also upload a local DMG or run **Desktop installers** for the same tag
   (same file names).
3. **Without the updater key**: run **Desktop installers** (`desktop-builds.yml`) as before; set
   `macos = true` to build the DMG in CI (signed/notarized if the Apple group exists, ad hoc otherwise)
   instead of uploading a local one.
4. Publish the release as a normal (not pre-) release: the IDE reads
   `releases/latest/download/latest.json`, and GitHub serves "latest" only for stable releases.
